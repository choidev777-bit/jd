## 2. 문제 정의 스토리 (기획 소재)

**F** 출발점은 "남들이 안 하고, 프로젝트가 끝나도 내가 계속 쓸 증권 툴"이었다. 사용자 조사에서 다수가 토스증권을 쓰는 걸 확인하고 토스의 기능을 분석했더니 실시간 어닝콜·실시간 이슈·실시간 커뮤니티 등 **전부 실시간에 초점**이 맞춰져 있었다. 그래서 반대로 **과거**에 집중했다. "오늘 오르는 테마의 소재와 비슷한 과거 이벤트를 찾아 그때 흐름을 보면 오늘 분석에 도움이 된다"는 가설. 테마주 데이터가 인포스탁에 정리돼 있는 걸 확인하고 온톨로지를 구축했다.

**F** 기획 단계에서 **4번 폐기**했다. 기준은 "이 프로젝트의 본질적 이유 = 증권·금융에 직접 연결된 서비스여야 좋은 평가를 받는다"였고, 팀원 아이디어(예: 공시 백과사전)는 1차원적이라 판단해 반려했다. 최종 아이디어는 팀장이 만들었다.

**→ 프레이밍**: "아이디어를 혼자 냈다"가 아니라 **"왜 만드는지를 기준으로 삼아 4번 기획을 폐기하고 다시 정의했다"**. 박인준 주임이 AIX 업무에서 가장 중요하다고 한 것이 "왜 만드는지를 개발팀에 설득하는 것"이라 정확히 겹친다. 경쟁 서비스 분석(토스) → 빈 자리 발견(과거) → 데이터 가능성 확인(인포스탁) → 기획 확정의 순서로 말하면 기획 논리가 산다.

⚠ 보강 필요: 반려된 팀원들의 반응, 최종 아이디어를 팀원들에게 어떻게 설명·납득시켰는지. 이 한 문단이 있어야 "독단"이 아니라 "설득"으로 읽힌다.

## 3. 서비스 구성 (발표 기준)

1. **실시간 테마 탐지와 소재 확인** — 강해지는 테마를 탐지하는 순간 관련 뉴스·상승 소재·주도주·확산 정도를 같은 화면에 연결. MTS를 나가 포털·텔레그램·커뮤니티를 돌지 않게 함
2. **데자뷰 분석(핵심)** — 오늘 Event와 닮은 과거 Event를 단어가 아니라 소재 유형·사건 주체·기대/확정 단계로 비교하고, 당시 주도주의 T+1·T+5·T+20 실제 결과를 연결. 소재가 하루 만에 소멸했는지, 테마 전체가 반응했는지 판단 기준 제공
3. **자연어 질문** — "이 정책 소재는 보통 하루 만에 끝났어, 며칠 이어졌어?" 같은 질문을 질의 유형·슬롯으로 변환 → 서버가 지식 그래프·가격 DB 조회·계산 → LLM은 검증된 결과를 문장으로만 표현. **AI가 수치를 만들지 않는 구조**

## 4. 기술 요약 (AI 면접용 — 개요 → 아키텍처 → 구현 순)

### 4-1. 데이터
- 인포스탁 테마 히스토리 **39,696건(2005~2026, 281테마)** + 일일 테마 시황 4,655건 — 분석 가능한 DB 형태로 제공되지 않아 **수집기를 직접 개발**
- 키움 수정종가 약 7.2M행 — **키움 REST API는 지정 IP 외 차단 → 고정 IP 서버(오라클 클라우드 VM) 사용**
- 발견한 문제: 같은 반도체 소재가 같은 날 HBM·CXL·반도체장비 등 9개 테마에 반복 기록 → 행을 세면 9건이지만 실제는 소재 1개에 테마 9개가 반응한 것. **원문 DB에 RAG만 붙이면 이 관계를 구분하지 못함** → 온톨로지 결정

### 4-2. Event Ontology
- 개념 정의: Theme(범주) · Catalyst(원인) · Event(특정 날짜에 소재가 발생해 테마가 반응한 한 번의 사건)
- 관계 구조: `Actor → Catalyst → ThemeReaction → Leader → Outcome → Evidence`
- 분류 4축: **소재 유형 28종**(복수 허용) / 상승·하락 방향 / 확실성(확정·기대·미명시) / 재부각 여부
- 결과: 원천 39,696건 → 중복 제거 Catalyst **20,008건** + ThemeReaction 39,696건. 사건 수와 사건당 반응 테마 수를 따로 계산 가능
- 어휘 설계: 전수 어절 빈도 분석 + 표본 1,000건 정독. "기타 10% 이하면 진행, 30% 이상이면 축 재설계" 규칙을 사전에 정함
- 어휘 버전·content hash를 라벨에 함께 저장 → 어떤 어휘로 분류했는지 재현 가능

### 4-3. 검증 ① — 사람 정답지 기반 정확도 루프
- 설계 표본과 겹치지 않는 새 표본 1,000건을 **팀원 4명이 각 1,000건씩 원문만 보고 블라인드 라벨링**(primary 유형 / 허용 대안 / 방향 / 확실성) → 정답지
- 정답지로 분류기 정확도 측정 → 오분류 케이스 보고 어휘·규칙 수정 → 재측정 반복
- dev 500 / test 500 분리. dev 87.8% vs **test 77.8%** → "dev를 보며 고쳤으니 77.8%가 실제 성능"으로 보고. 방향 99.6%, 확실성 90.0%
- 희소 유형은 30건 미만이면 "측정 불가"로 표시하고 해당 질문 유형을 열지 않음. 희소 유형 보강 표본 910건 추가
- 라벨 출처 3등급(HUMAN_CONFIRMED / AI_DRAFT / AI_CROSS_CHECKED) — **승격 판정은 HUMAN_CONFIRMED만 인정**

### 4-4. 검증 ② — Ragas 비교
동일 질문 80개, 원천 데이터·LLM·프롬프트 고정, 검색 방식만 변경:

| 방식 | Context Precision | Context Recall | Faithfulness | Factual Correctness |
|---|---:|---:|---:|---:|
| Keyword RAG | 0.54 | 0.63 | 0.66 | 0.60 |
| Vector RAG | 0.65 | 0.74 | 0.71 | 0.67 |
| Hybrid RAG | 0.74 | **0.84** | 0.79 | 0.76 |
| **Ontology/KG-RAG** | **0.85** | 0.82 | **0.88** | **0.84** |

→ Recall은 Hybrid가 약간 높지만 불필요한 문서를 줄이고 더 정확한 근거로 답함.

### 4-5. 아키텍처
- 모듈형 모놀리스 코드베이스 + 역할별 독립 프로세스(API / 실시간 시장 worker / 뉴스 worker / 배치 worker)
- PostgreSQL(장기 데이터·원문) + Redis(장중 상태). 과거 조회 REST, 실시간 갱신 WebSocket
- Python 3.12·uv·FastAPI 계열(uvicorn)·psycopg / React·Vite·TypeScript / Docker Compose·Caddy / OCI(백엔드) + Vercel(프론트) / Alembic 마이그레이션 10개
- OpenAPI·JSON Schema 기계 계약, ADR 문서, PRD·screen_spec·api_contract 분리
- 테스트 722건 통과(2026-08-17 기준), ruff·mypy

## 6. AI 개발 워크플로우 (AI 거버넌스 소재 — 이 프로젝트의 최대 차별점)

**F** 코드는 AI(Claude Code)가 작성. 사람은 설계·기능 정의·명세 문서화와 **AI가 코드를 만들어내는 시스템의 설계·통제**를 담당.

1. 아이디어·요건을 `docs/`에 문서로 정리 (PRD, 화면 명세, API 계약, 구현 로드맵)
2. `CLAUDE.md`에 컨텍스트 고정 — 코딩 컨벤션, 폴더 구조, 테스트 실행법, 금지사항. AI가 매번 프로젝트 맥락을 새로 파악하지 않게 함
3. 작업 분해 — AI가 한 번에 처리하고 빠르게 검증할 수 있는 작은 단위로 쪼개고 단위마다 완료 조건 명시. 크게 던지면 방향 오류를 늦게 발견함
4. **계획 먼저** — 코드를 바로 짜게 하지 않고 "어떻게 구현할지 계획만" 받아 검토·수정 후 실행 승인
5. **테스트 우선** — 실패하는 테스트를 먼저 쓰게 하고 통과하는 코드를 구현. "다 됐다"는 말을 믿지 않고 테스트 통과로 판단. 린트·타입체크·테스트 실행 → 에러 로그 붙여 수정 → 반복. 이 루프는 자동화
6. **세션 분리 리뷰** — PR 전 다른 세션·다른 모델에게 "보안 취약점, 성능 문제, 누락된 엣지 케이스"를 찾게 함. 작성 세션과 리뷰 세션 분리가 핵심
7. CI에 AI 리뷰 봇을 붙여 필터링

**CLAUDE.md에 명문화한 규칙 예시**
- 요청한 것만 구현. 요청하지 않은 추상화·옵션·방어 코드 추가 금지
- 범위를 스스로 줄이지 않음. "MVP니까 이 정도만" 제안 금지. 다 못 하면 무엇을 왜 못 했는지 보고
- 새 문서 생성 금지(명시 요청 시만). 결과는 커밋 메시지와 응답으로 보고
- **사람 승인이 필요한 3가지**: 실제 배포·클라우드 리소스 변경 / 외부 API 실호출 수집 / 파일·데이터 삭제
- 완료는 "했다", 미완료는 "안 했다". 추정을 완료로 쓰지 않음

**→ AIX 매핑**: JD "AI 거버넌스(위험평가 등) 운영" · 김재헌 "AIX 팀장은 AI 역량과 소통을 본다" · 박인준 "요건 정의 → 문서화 → 개발팀 전달 → 검토". 개발팀 자리에 AI가 있을 뿐 구조가 같다. **"AI에게 일을 맡길 때 무엇을 문서로 고정하고, 어디서 사람이 승인하고, 어떻게 검증하는가"를 직접 설계·운영한 경험**으로 말할 것.

## 10. 예상 꼬리질문과 답 방향

- **온톨로지가 뭐냐, 쉽게** → 글 속 정보에 역할(주체·원인·반응·결과·근거)을 붙여 연결한 지식 지도. 문장을 찾는 게 아니라 사건을 세고 비교할 수 있게 하는 구조
- **RAG로 안 되는 이유** → 같은 소재가 9개 테마에 9행으로 기록 → RAG는 비슷한 문장을 찾지만 "사건 1개·반응 9개"라는 관계를 못 셈
- **Ragas가 뭐냐** → RAG 답변 품질을 근거 정확도·근거 재현율·답변 충실도·사실 일치도로 측정하는 평가 프레임워크. 같은 질문·같은 LLM에서 검색 방식만 바꿔 비교
- **77.8%면 낮은 거 아니냐** → 28종 다중 분류의 엄격 일치 기준이고 dev 점수(87.8%)가 아닌 test를 보고한 것. 방향 99.6%·확실성 90%. 30건 미만 유형은 "측정 불가"로 막아 낮은 구간이 서비스에 노출되지 않게 함
- **AI가 코드 다 짰으면 네 역량은 뭐냐** → 요건·명세·완료 조건을 정의하고, 계획을 검토·승인하고, 테스트와 세션 분리 리뷰로 검증하는 시스템을 설계·운영한 것. AI가 만든 결과를 믿지 않고 측정한 것(6장·4-3)
- **팀원들은 뭘 했나** → 5장 표 + 라벨링 4,000건 + 프론트·UI/UX 병렬 작업 구조. ⚠ 설득 에피소드
- **느려지면?** → 7장 보정 답
- **실서비스로 만들려면?** → 인포스탁 데이터 권리, 컴플라이언스(투자 판단 오인 방지 문구), 검수 인력, 2인 라벨 검증. 키움 내부라면 망분리 환경에서 LLM 호출 경로 설계가 선행
- **키움 사내 업무에 적용하면?** → 인포스탁 대신 사내 문서·업무 기록에 같은 방식(통제어휘 → 라벨 → 정답지 검증 → LLM은 설명만) 적용. AIX의 사내 LLM 활용도 문제와 연결

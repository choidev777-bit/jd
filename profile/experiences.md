# 경험 카드

jobjob-write 스킬은 이 파일에 있는 경험만 자소서에 쓴다. 여기 없는 경험은 지어내지 않고 인터뷰로 묻는다.
jobjob-intake 스킬과 jobjob-write 스킬의 인터뷰가 아래 양식으로 카드를 추가한다.

출처: profile/raw/경험노트1~3 (2026-09-06 정리). 사실(F)만 옮겼고, 노트의 프레이밍 제안(→)은 applications/2026-09-키움증권-AIX/strategy.md에 있다.
"배운 점"은 원본에 본인 확인 문장이 없어 후보만 적고 (인터뷰 필요)로 남겼다.

## 카드 양식

```
### [경험 제목] (기간, 소속)
- 상황: 어떤 문제나 과제가 있었나
- 역할: 팀에서 내가 맡은 것 (팀 성과와 내 기여를 구분)
- 행동: 내가 구체적으로 한 일
- 결과: 수치나 비교 가능한 사실
- 배운 점: 한 문장
- 관련 역량: (예: 데이터 분석, 협업, 문제 해결)
- 쓰기 좋은 문항: (예: 직무역량, 실패 극복)
```

### DAY-JA-VIEW, 테마 이벤트 스터디 도구 (2026-08, 키움 디지털 아카데미 4기 최종 프로젝트)
- 상황: 주제 제한 "금융 관련 디지털 서비스", 5인 팀, 약 2주 반. 사용자 조사에서 다수가 쓰는 토스증권이 실시간 어닝콜·이슈·커뮤니티 등 전부 실시간에 초점을 둔 것을 보고 반대로 "과거"에 집중. 오늘 급등 테마의 상승 소재와 닮은 과거 사건을 찾아 당시 주도주의 T+1·T+5·T+20 결과를 근거와 함께 보여주는 도구. 인포스탁 테마 히스토리 39,696건(2005~2026, 281테마)에서 같은 소재가 같은 날 9개 테마에 반복 기록되는 문제를 발견, 원문에 RAG만 붙이면 "소재 1개에 테마 9개 반응" 관계를 구분하지 못해 이벤트 온톨로지로 설계
- 역할: 팀장. 아이디어·기획·PM·백엔드·문서화(PRD, 화면 명세, API 계약, ADR)·발표와 Q&A 전담. 팀원은 프론트엔드 1명, 발표자료 1명, UI/UX 2명. 팀원 4명이 온톨로지 정답지 라벨링 각 1,000건 담당
- 행동:
  - "왜 만드는가"(증권·금융에 직접 연결된 서비스)를 기준으로 기획을 4번 폐기하고 재정의
  - 인포스탁 데이터가 분석 가능한 DB 형태로 제공되지 않아 수집기 직접 개발. 키움 REST API가 지정 IP 외 차단이라 고정 IP 서버(오라클 클라우드 VM) 구성. 키움 수정종가 약 7.2M행
  - Event Ontology 설계: Actor → Catalyst → ThemeReaction → Leader → Outcome → Evidence 관계, 분류 4축(소재 유형 28종·상승/하락·확정/기대/미명시·재부각). 원천 39,696건 → 중복 제거 Catalyst 20,008건. 어휘는 전수 어절 빈도 + 표본 1,000건 정독으로 설계, "기타 10% 이하면 진행, 30% 이상이면 축 재설계" 규칙을 사전에 정함
  - 검증 ①: 설계 표본과 겹치지 않는 새 표본 1,000건을 팀원 4명이 블라인드 라벨링해 정답지 작성 → 분류기 정확도 측정 → 오분류 보고 어휘·규칙 수정 → 재측정 반복. dev 500 / test 500 분리. 30건 미만 희소 유형은 "측정 불가"로 표시하고 해당 질문 유형을 열지 않음. 라벨 출처 3등급(HUMAN_CONFIRMED / AI_DRAFT / AI_CROSS_CHECKED) 중 HUMAN_CONFIRMED만 승격 인정
  - 검증 ②: 동일 질문 80개, 원천·LLM·프롬프트 고정, 검색 방식만 바꿔 Keyword·Vector·Hybrid·온톨로지 RAG를 Ragas로 비교
  - 자연어 질문은 질의 유형·슬롯으로 변환 → 서버가 지식 그래프·가격 DB 조회·계산 → LLM은 검증된 결과를 문장으로만 표현(AI가 수치를 만들지 않는 구조)
  - 아키텍처: 모듈형 모놀리스 + 역할별 독립 프로세스(API / 실시간 시장 worker / 뉴스 worker / 배치 worker), PostgreSQL + Redis, REST + WebSocket. Python 3.12·FastAPI 계열·React·TypeScript·Docker Compose·OCI + Vercel. ruff·mypy
  - AI 코딩 워크플로우 설계·운영: 요건을 docs/에 문서화 → CLAUDE.md에 컨벤션·구조·금지사항 고정 → 작업을 작은 단위로 분해하고 완료 조건 명시 → 계획 먼저 받아 검토 후 실행 승인 → 실패 테스트 먼저 쓰고 통과 코드 구현(린트·타입체크·테스트 루프 자동화) → PR 전 다른 세션·모델에 보안·성능·엣지 케이스 리뷰 → CI에 AI 리뷰 봇. 사람 승인 3원칙(실제 배포·클라우드 변경 / 외부 API 실호출 / 파일·데이터 삭제)
- 결과: 5개 팀 중 1위. 심사위원 7인(인사이트랩·X-STUDIO·AIX·플랫폼전략) 평균 52.6/60. 항목별 기술 완성도 9.1, 발표·문서화 9.1, 기획 8.9, 데이터 활용 8.9, UI/UX 8.7, 팀워크 7.9. 분류기 test 정확도 77.8%(dev 87.8%, 방향 99.6%, 확실성 90.0%). Ragas: 온톨로지 RAG Context Precision 0.85 · Context Recall 0.82 · Faithfulness 0.88 · Factual Correctness 0.84로 Hybrid RAG(0.74·0.84·0.79·0.76) 대비 Recall 외 전부 우위. 348 커밋, 테스트 722건, 문서 30여 종, 웹 서비스 배포(dayjaview.vercel.app)
- 배운 점: (인터뷰 필요. 후보: "AI가 만든 결과는 믿지 않고 측정한다" / "판단은 검증 가능한 데이터·구조에 맡기고 LLM은 설명에 쓴다")
- 관련 역량: 문제 정의·기획, 요건 문서화, 백엔드, AI 검증 설계, AI 작업 거버넌스, 작업 분해·위임
